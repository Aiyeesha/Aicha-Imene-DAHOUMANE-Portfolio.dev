Déployer en production est l'un des moments les plus risqués dans tout projet Salesforce. Choisir le mauvais outil — ou utiliser le bon outil incorrectement — mène à des métadonnées manquantes, des dépendances cassées et des rollbacks d'urgence. Voici une comparaison pratique des trois options principales.

---

## Les trois méthodes en un coup d'œil

| Méthode | Idéal pour | Courbe d'apprentissage | Prêt CI/CD |
|---------|-----------|------------------------|------------|
| Change Sets | Petites orgs, déploiements occasionnels | Faible | ❌ |
| Salesforce CLI (SFDX) | Développeurs, automatisation | Moyenne | ✅ |
| DevOps Center | Équipes, pipelines, sans code | Faible–Moyenne | ✅ |

---

## Change Sets — Simple mais limité

Les Change Sets fonctionnent entièrement au clic : vous ajoutez les composants dans l'org source, vous chargez le change set, puis vous le déployez depuis l'org cible. Aucun terminal requis.

**Quand les utiliser :**
- Petite org avec des déploiements peu fréquents
- Admin non technique effectuant des changements de configuration
- Hotfix d'urgence ponctuel

**Limites strictes à connaître :**
- Aucun mécanisme de rollback — vous devez annuler les changements manuellement
- Aucune vue des différences — vous ne savez pas ce qui change par rapport à la cible
- Impossible de déployer des changements destructifs (suppression de champs/objets)
- Aucune automatisation — chaque déploiement est manuel
- Aucune gestion de version (pas de Git)
- Dépendances non résolues automatiquement → erreurs de déploiement fréquentes

```bash
# Pas d'équivalent CLI — les Change Sets se gèrent uniquement dans l'interface :
# Setup → Deploy → Outbound Change Sets → New
```

> **Astuce :** si vous faites plus d'un déploiement par sprint, les Change Sets vont vous ralentir. Il est temps de passer à SFDX.

## Salesforce CLI (SFDX) — Le standard des développeurs

SFDX traite les métadonnées de votre org comme du code source stocké dans un dépôt Git. Vous déployez avec la commande `sf` (CLI v2).

**Installation :**

```bash
# Installer la SF CLI
npm install -g @salesforce/cli

# S'authentifier sur votre org
sf org login web --alias my-sandbox

# Récupérer les métadonnées de l'org vers le projet local
sf project retrieve start --target-org my-sandbox

# Déployer la source locale vers l'org
sf project deploy start --target-org my-sandbox

# Valider sans déployer (simulation)
sf project deploy validate --target-org my-sandbox --test-level RunLocalTests
```

**Récupérer et déployer de façon ciblée :**

```bash
# Ne récupérer que certains types de métadonnées
sf project retrieve start \
  --metadata ApexClass,CustomObject,Layout \
  --target-org my-sandbox

# Simuler le déploiement avec exécution des tests, sans rien enregistrer
sf project deploy start \
  --source-dir force-app \
  --target-org production \
  --test-level RunLocalTests \
  --dry-run
```

**Structure du projet :**
```
force-app/
  main/
    default/
      classes/        ← Classes Apex
      triggers/       ← Triggers Apex
      lwc/            ← Lightning Web Components
      objects/        ← Objets/champs personnalisés
      flows/          ← Flows
      permissionsets/ ← Permission Sets
```

**Changements destructifs** (suppression de métadonnées) :

```bash
# Créer destructiveChanges.xml puis déployer
sf project deploy start \
  --manifest destructiveChanges.xml \
  --target-org production \
  --test-level RunLocalTests
```

**Quand utiliser SFDX :**
- Toute équipe qui utilise Git
- Projets dotés d'un pipeline CI/CD (GitHub Actions, GitLab CI)
- Quand vous avez besoin de déploiements reproductibles et auditables

## DevOps Center — Des pipelines d'équipe sans code

DevOps Center est l'outil de pipeline intégré à Salesforce (disponible depuis Winter '23). Il crée un pipeline adossé à Git avec des environnements (Dev → QA → UAT → Production) et assure le suivi des work items.

**Fonctionnalités clés :**
- Interface visuelle du pipeline directement dans le Setup Salesforce
- Intégration Git automatique (GitHub, GitLab, Bitbucket)
- Promotion des changements d'une étape à l'autre en un clic
- Détection des conflits entre branches parallèles

**Quand utiliser DevOps Center :**
- Équipes mixtes (admins + développeurs)
- Vous voulez l'intégration GitHub sans écrire de YAML
- Plusieurs sandboxes avec un processus de promotion formel

**Flux typique :**
1. Créer un Work Item dans DevOps Center
2. Associer les modifications à ce Work Item
3. Promouvoir vers l'environnement suivant (Dev → UAT → Prod)
4. DevOps Center gère automatiquement les commits Git

**Limite :** il ne remplace pas un pipeline CI/CD complet — aucune barrière de tests automatisés n'est intégrée. Il vous faut toujours GitHub Actions ou un équivalent pour imposer les tests.

## Pipeline CI/CD avec SFDX + GitHub Actions

Pour les projets sérieux, combinez SFDX et GitHub Actions :

```yaml
# .github/workflows/deploy.yml
name: Deploy to Sandbox

on:
  push:
    branches: [develop]

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Install SF CLI
        run: npm install -g @salesforce/cli

      - name: Authenticate to sandbox
        run: |
          echo "${{ secrets.SF_AUTH_URL }}" > auth.txt
          sf org login sfdx-url --sfdx-url-file auth.txt --alias sandbox

      - name: Validate and deploy
        run: |
          sf project deploy start \
            --target-org sandbox \
            --test-level RunLocalTests \
            --wait 30
```

## Pièges courants

- **Dépendances manquantes** : lancez toujours `sf project deploy validate` avant de pousser en production — cela détecte les références manquantes
- **Conflits de profils** : les profils sont notoirement difficiles à fusionner ; utilisez plutôt des Permission Sets et excluez les profils des déploiements quand c'est possible
- **Déployer trop de choses** : limitez vos déploiements aux seuls composants modifiés avec `--manifest package.xml`, et non à tout `force-app/`
- **Aucun plan de rollback** : documentez un script de rollback avant chaque déploiement en production. Salesforce ne propose pas de rollback en un clic
- **Oublier les tests** : ne déployez jamais en production avec `--test-level NoTestRun`
- **Change Sets pour des projets complexes** : les dépendances non résolues provoquent des erreurs en cascade
- **Ignorer le `.forceignore`** : comme `.gitignore`, il exclut du déploiement les fichiers non pertinents

---

## Checklist de décision

- [ ] Admin seul, petite org, déploiements rares → **Change Sets**
- [ ] Développeur, projet basé sur Git, quelle que soit la taille → **SFDX**
- [ ] Équipe aux niveaux techniques variés, étapes formelles → **DevOps Center**
- [ ] Tout déploiement en production → lancer au minimum `--test-level RunLocalTests`
- [ ] Grandes équipes → imposer `RunAllTestsInOrg` dans la CI
